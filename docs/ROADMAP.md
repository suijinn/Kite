## 3. フェーズ 1 — 安定性（最優先）

要件 13 の残課題と、常用に入る前に潰しておくべきもの。

### P1-1. シェル拡張の別プロセス化 `kite_shellhost.exe` — ✅ 完了

`IContextMenu` のハンドラ（Box、Google Drive、7-Zip、TortoiseGit …）は
`kite_shellhost.exe` の中だけで動く。拡張が確保したメモリを壊しても、裏でスレッドを
立てて落ちても、失われるのはメニュー 1 回分とホストプロセスだけ。次の要求で黙って
起動し直す。これで要件 13 が埋まった。

構成は `ShellHostProtocol.h`（交換する書式。Windows 非依存で `tests/test_hostproto.cpp`
が直接検証）、`ShellPipe.cpp`（名前付きパイプ）、`ShellHostClient.cpp`（`kite.exe` 側）、
`ShellMenu.cpp`（`IContextMenu` 本体。**ホストだけがリンクする**）、
`tools/shellhost/main.cpp`（ホストの入口）。

core / ui 側の変更は `IShellIntegration` の戻り値が `void` から `bool` になった
（メニューを出せなかったことを status 行に出す）だけ。設計上の判断は CLAUDE.md の
「シェル拡張の隔離」、残っている制限は同「現時点の弱点」。

### P1-2. 元に戻す（Ctrl+Z）— ✅ 完了

`Ctrl+Z`（`Cmd::Undo`）が、**名前の変更・新規作成・移動・コピー・ごみ箱への削除**を
元に戻す。履歴は `core/app/UndoStack`（OS にも描画にも触れない）が持ち、逆操作は
`App::DoUndo` が `IFileSystem`（削除だけは `IShellIntegration`）を通して行う。
`tests/test_undo.cpp` が端から端まで検証する。

**シェル任せにはできなかった。** `FOF_ALLOWUNDO` はシェルの Undo スタックに積むが、
そこを呼ぶ公開 API が無い。加えて名前の変更は `MoveFileExW` なので、そもそもそのスタックに
載らない ─ シェル任せにすると「F2 で付けた名前を戻す」という一番よく要る操作が
最初から対象外になる。

**ごみ箱への削除は戻せる。** 履歴が覚えるのは**消される前のパス**で、ごみ箱の中で
名乗る `$R` の名前ではない ─ 削除の時点で分かっているのがそちらしかなく、控えるには
削除のたびにごみ箱を引き当て直すことになって、一度も `Ctrl+Z` を押さない人まで
その代金を払うことになる。突き合わせは戻すときに 1 回だけ行い、「元の場所」
（`PID_DISPLACED_FROM`）と項目名から元のパスを組み立てて比べる。同じパスの項目が
複数あれば**最後に消したもの**を採る（`PID_DISPLACED_DATE`）─ `Ctrl+Z` が指している
のは常に直前の削除なので、それが正しい答えになる。

**完全削除だけは戻せない。** 履歴に「戻せない印」（`UndoKind::Erase`）を積み、`Ctrl+Z`
はそこで止まって理由を言う ─ 飛び越えると、消えたファイルはそのままにその前の
名前変更だけが巻き戻る。**ごみ箱への削除ではこの印を積まない**（戻せる以上、その下の
操作が到達不能になる理由が無い）。設計上の判断は CLAUDE.md の「元に戻す」と
「`Ctrl+Z` で削除を戻す」。

### P1-3. 単一インスタンス化 — ✅ 完了

2 つ目の起動は、既存のウィンドウへパスを渡して自分は黙って終わる。パスは
そのウィンドウの新しいタブになり、ウィンドウが前面に出る。目印（ミューテックス名と
ウィンドウクラス名）は **exe のフルパスから導く**ので、別フォルダに展開した 2 つの
コピーは別のインスタンスとして動く ─ 固定名にすると、一方の `config` だけが使われる
（CLAUDE.md「設定の置き場所」）。

`--new-window` が付いた起動だけがこの検出を通らない。`Ctrl+N`（`Cmd::NewWindow`）が
使うのがこの引数で、今や「本当に新しい窓が要る」と言える唯一の手段。

| ファイル | 役割 |
| --- | --- |
| `platform/win/WinSingleInstance.cpp` | 目印の生成、既存ウィンドウの探索、`WM_COPYDATA` の送受形式 |
| `src/main_win.cpp` | 起動時の振り分け |
| `App::OpenForwardedPaths` | 受け取ったパスをタブとして開く |

設計上の判断は CLAUDE.md の「単一インスタンス」。

### P1-4. エラー処理の網羅 — ✅ 完了

**失敗は必ず言う。** 名前の変更・作成・削除・コピー・移動・元に戻すは、失敗したら
何が失敗したかをステータス行に出す（`App::ReportFailure`）。以前は OS の文言を
そのまま流していたので、`ErrorText()` が文言を持たないコードでは**何も出ないまま
操作だけが失敗した** ─ 画面が何も変わらないので「キーが効かない」と読める。
設計上の判断は CLAUDE.md の「失敗の伝え方」。

| 潰したもの | どうしたか |
| --- | --- |
| アクセス拒否フォルダ | 一覧はエラー行を出し、`..` も出さない。UNC なら `Ctrl+Shift+L` を案内 |
| ロック中ファイルのリネーム | 「名前を変更できませんでした」＋ OS の文言。履歴には積まない |
| 260 文字超のパス | 規則を `path::ToExtended()`（core）へ移して検証。**拡張パスには OS の正規化が掛からない**ので、付ける前に `Normalize()` を通す |
| 列挙中のドライブ切断 | `FindNextFileW` が落ちたら**半分の一覧を捨てる**。デバイス系のコードを `Unavailable` に振る |
| オフラインのクラウドフォルダ | `ERROR_CLOUD_FILE_*` を `Unavailable` / `AccessDenied` に振る。空のフォルダとして出さない |
| シェル操作の失敗 | `SHFileOperation` の `DE_*` を Win32 コードへ写して OS の言葉で出す。利用者の取り消しは失敗にしない |

検証は `tests/test_app.cpp`（失敗の伝わり方）、`tests/test_pathutil.cpp`（拡張パス）、
`tests/test_utf8.cpp`（UTF-16 換算の長さ）。`FakeFileSystem::locked` が、
OS が何も言わない失敗を含めて再現する。

`.github/workflows/ci.yml` が main への push と PR で回る。ビルド＋全テスト

## 4. フェーズ 2 — エクスプローラー機能パリティ

要件 6 を埋める。ここまで来ると「常用してエクスプローラーを無効化できる」水準。

### P2-1. 仮想フォルダ（「PC」「ごみ箱」「ネットワーク」）— ✅ 完了

3 つともサイドバーの先頭に並び、開いて辿れる。「PC」からドライブへ入れば普通のフォルダ
（`C:\`）になり、`Alt+↑` で戻れば「PC」に出る ─ `\\server` の上が「ネットワーク」に
なるのも同じ規則（`vfs::ParentOf`）。名前空間拡張が作る入れ子のフォルダ（iCloud フォト
など）もそのまま開ける。

`WinShellFileSystem` を別に立てるのではなく、`WinFileSystem::List` が `virtual:` の付いた
パスだけを振り分ける形にした。**実 FS の高速経路には一切触れていない。** `fs::Entry` に
足したのは PIDL ではなく `address` という文字列 1 本で、実フォルダの項目では空のまま ─
10 万件のフォルダで 1 件ずつ std::string を増やす代償を払わない。

**列挙は `kite_shellhost.exe` の中だけ。** `IShellFolder::EnumObjects` は名前空間拡張の
DLL を呼び出し元プロセスに読み込ませる（「PC」を開くと iCloud の拡張が起き上がるのを
実測した）。P1-1 / P2-10 で追い出したものと性質が同じなので、3 つ目のホストとして同じ
仕組みに乗せてある。読み取りには 30 秒の制限がある ─ 名前空間拡張の列挙は中断できない
ので、返ってこない相手にできるのはホストごと捨てることだけ。

| ファイル | 役割 |
| --- | --- |
| `core/fs/VirtualPath.h` | `virtual:` の規則と 3 つの根、`..` の行き先（`tests/test_vfolder.cpp`） |
| `platform/win/VirtualNames.cpp` | Kite の綴りとシェルの解析名の相互変換。**ホストは前置を知らない** |
| `platform/win/ShellFolder.cpp` | `IShellFolder` の列挙本体。**`kite_shellhost.exe` だけがリンクする** |
| `platform/win/FolderHostClient.cpp` | ホストへの要求（時間制限あり、ワーカー間で直列化） |
| `platform/win/ShellFolder.cpp` の `ResolveItemsInFolder` | 「フォルダ + 解析名」から項目の PIDL を引き当てる |

**ごみ箱の項目は「どのフォルダの中の項目か」ごと渡して指す。** 消した項目の解析名は
隠された `$R` の写しのパスなので、そのまま解析するとごみ箱の項目ではなく**ただの
ファイル**が返り、その親はごみ箱ではないので「元に戻す」がどこにも現れない。要求に
フォルダを添えると（`shellhost::Request::container`）、ホストはそのフォルダを列挙して
解析名の一致する子の PIDL を組み立てる ─ 得られる絶対 PIDL の親はごみ箱そのものなので、
メニューもアイコンも今までどおりの道を通る。**PIDL をホスト側の表に置いて id を配る形は
採らなかった**（世代がずれた id は「別のファイルを消す」になる）。

**復元は `Alt+R`（`Cmd::Restore`）。** 実体はシェルの `undelete` 動詞で、右クリックの
メニューにも「元に戻す」が正しく並ぶ。設計上の判断は CLAUDE.md の「仮想フォルダ」と
「ごみ箱の項目を正しく指す」。

### P2-2. ZIP をフォルダとして開く — ✅ 完了

一覧で `.zip`（と `.cab`）を開くと、中身がそのまま一覧に出る。ZIP はシェル名前空間
拡張として見えるので、**列挙もアイコンもメニューも P2-1 の経路がそのまま通った** ─
足したのは入口の判断（`App::ActivateEntry` が `shell_.Open()` ではなく
`vfs::ArchivePath()` を通して `OpenPath()` を呼ぶ）と、実 FS との境目をどこに置くか
だけ。判断は `core/fs/VirtualPath`（OS にも描画にも触れない）が持ち、
`tests/test_vfolder.cpp` と `tests/test_app.cpp` が端から端まで検証する。

**下地でまかなえなかったのは 4 つ。** (1) `..` は書庫そのものから**実フォルダへ抜ける**
必要があった ─ 書庫の縁がシェル名前空間と実 FS の境目で、そこで止めると `Alt+↑` も
パンくずも中から出られない。(2) 書庫の中の項目は、シェルが `SFGAO_FILESYSTEM` を
立ててきても実 FS ではない ─ 解析名がパスの綴りそのものなので、信じると開いた瞬間に
「利用できません」になる。(3) `path::Normalize` が `virtual:` の前置を 1 つの構成要素
として畳んでいて、**UNC 上の書庫で先頭の `\\` が 1 本になっていた。**
(4) 中のファイルを開くのに `ShellExecute` もシェルの「開く」動詞も使えなかった ─
前者はその綴りのファイルがディスクに無いので開けず、後者は explorer.exe が呼び出し元
プロセスからデータを吸い出す作りなので、**空のファイルが開いた。** `IFileOperation` で
`%TEMP%` へ同期的に写しを作り、出来上がった実ファイルを開いている。

**既定は「フォルダとして開く」**（`[ui] open_archives`、設定画面「ZIP をフォルダとして
開く」）。展開ソフトを入れている人の答えは違うので設定にしてあるが、既定を off にすると
機能が在ること自体が伝わらないうえ、on でも失う操作は無い ─ 右クリックのメニューには
シェルのものがそのまま出る。設計上の判断は CLAUDE.md の「ZIP をフォルダとして開く」。

### P2-3. 検索 — **M**

自前で歩く（インデックス未作成のフォルダでも効くほうが実用的）。

主な変更: `core/fs/` に `SearchJob`、`Tab` に「検索結果モード」、`Cmd::Search`。

### P3-1. コマンドパレット — ✅ 完了

決めたこと:

- **絞り込みはラベル・分類・`keys.ini` 上の名前の 3 つに当てる。** 設定ファイルで見た
  `tab.new` を打つ人がいて、しかもそれは表示言語で動かない唯一の綴り。**当たる 3 つは
  3 つとも行に出す** ─ 出ていない条件で絞り込めることは、誰にも伝わらない。
- **並びはコマンド表の定義順。** 使用頻度で並べ替えると、探している行が打鍵ごとに動く。
- **`Enter` だけが実行。** `Ctrl+Enter` に «別の実行のしかた» は無いので、意味を作らない。
- **自分自身の行は出さない。** 選ぶとパレットが閉じて開き直るだけの行き止まりになる。
- **割り当ての無いコマンドには「未割り当て」と出す。** 何も書かない行は「窓が狭くて
  切れた列」と見分けが付かないうえ、«どれにキーが無いのか» はこの画面が答えるべき問い。
- **絞り込みは小さな添え書きではなく入力欄。** 打ち込む相手なので、文字の大きさで器を
  作り、キャレットとアクセント色の縁を持たせる。ブックマーク一覧も同じ器を使う。
- **並べるのはコマンドの «表» で、実行中に増減する «データ» は並べない**（行き先の窓口は
  P3-12）。ブックマークを行として足すと、次はタブ、セッション、ドライブを断る理由が
  無くなる。ただし番号で指す
  8 個（`Alt+Shift+1..8`）には**行き先の名前を添える** ─ 「ブックマーク 1 へ」は画面に
  出ていない一覧の «何番目» を指すだけで、それ単体では読めない行だった。行は増えないので
  «データを並べる» ことにはならず、9 件目以降は `Ctrl+P` の仕事のまま。
- **パネルの寸法は窓だけで決める。件数では決めない。** 一致件数で決めると打鍵のたびに
  パネルが縮み、絞り込み前の件数で決めると画面ごとに高さが変わる ─ パレットから
  `nav.places` を選んだ瞬間に、打ち込んでいた入力欄が別の場所へ飛ぶ。行き先の一覧と
  パレットは同じ大きさで出る。
- **実行するのは `App`。** `HandleKey()` は「何をすべきか」を返すだけ ─ この画面が
  コマンドを実行し始めた時点で «選ばせるもの» ではなくなる（ブックマーク一覧と同じ）。

### P3-4. 型入力ジャンプ（type-ahead）— ✅ 完了

文字キーを押すと、その名前で始まる行へカーソルが飛ぶ。`Ctrl+F` の絞り込みとは別物で、
**行は 1 つも消えない** ─ 打った文字は 1.2 秒で消え、ステータス行に出る。同じ文字を
続けて打つと次の候補へ回り、打ち足せば絞り込まれる。

`Space` の衝突は「打っている最中かどうか」で捌いた ─ 打ちかけの文字列が無ければ
今までどおり選択のトグル、ある間は名前の一部として受け取る。`Backspace` と `Escape` も
同じ読み方で、打っている間だけ打ちかけの文字列のものになる。

**既定バインドは文字キー単独と `Shift+<文字>` を空けたまま残してある** ─ 修飾は必ず
`Ctrl` か `Alt` が付く。ここを埋めると、大文字小文字を畳んで飛ぶこの機能と
「`b` は項目へ、`B` は別の何かへ」という形で必ず食い違う。

判断はすべて `core/input/TypeAhead`（OS にも描画にも触れない）にあり、

### P3-12. 行き先の検索 — 🟡 部分的

`Alt+B` だった「ブックマークの一覧」を **`Ctrl+P` の行き先の一覧**に育てる。ブックマーク・開いている
タブ・ドライブ・履歴を 1 つの入力欄から絞り込んで飛ぶ、移動のための窓口。

**なぜコマンドパレットに混ぜないのか。** 「1 つの万能な窓口があれば便利」は正しい要求だが、
混ぜると**頻度の高い側が代金を払う**。ファイラーの主動詞は移動で、行き先は実行中に増減する
データ（ブックマーク数十件、タブ数枚）。対してコマンドは 124 行の固定表で、覚えた人は和音を
使う ─ パレットは「割り当てを覚えていない・奪われた」ときの窓口として稀に使われる側である。
両者を 1 つの一覧にすると:

- **絞り込みが薄まる。** `d` と打った瞬間に `file.delete`・`tab.duplicate`・`Downloads` が
  並ぶ。探しているのはたいてい後者なのに、行数は前者のほうが桁違いに多い。
- **順位付けが必須になる。** 毎日使うブックマークが一度も使わないコマンドより下に出るのは
  許容できないので、使用頻度と最近使った順を覚える場所が要る。これは
  **「探している行が打鍵ごとに動くと、目で追うより打ち直すほうが速くなる」**（P3-1）に
  正面から反する。

そこで「窓口を 1 つに」ではなく**頻度の高い側に良い和音と行の種類を渡す** ─ VS Code が
`Ctrl+P`（場所）と `Ctrl+Shift+P`（コマンド）を分け、短い和音を前者に与えているのと同じ
判断。パレットからは `nav.places` の行 → `Enter` で開くので、道は 1 打鍵ぶん長いだけで
通じている。

段取り:

1. **行の種類を増やす** — ✅ 開いているタブ（`PlacePicker::OpenTab`）、✅ ドライブ
   （`fs::Root`）。⬜ クイックアクセス、⬜ 履歴（`Tab::history`）。器は `PickerList` と
   `AppUi::PaintPickerFrame` にあるので、増えるのは行の組み立てと «選ばれたときに何をするか»
   だけ。
2. **和音を格上げする** — ✅ `Alt+B` → **`Ctrl+P`**。移動のほうが頻繁なのだから、
   コマンドパレット（`Ctrl+Shift+P`）より打ちやすい席をこちらに渡した。**既存環境では
   `Alt+B` が残る**（`keys.ini` にその行が書かれているため。`Ctrl+N` と同じ罠で、案内する
   ときはそれを踏まえる）。同じ段で改名も済ませた: `BookmarkPicker` →
   `PlacePicker`、`Cmd::ShowBookmarks` → `Cmd::ShowPlaces`、`Hit::BookmarkRow` →
   `Hit::PlaceRow`、`cmd.show_bookmarks` → `cmd.show_places`（表示は「行き先の一覧」）。
   3 段目で `keys.ini` の名前も `bookmark.list` → **`nav.places`** に揃え、分類も
   ブックマークから移動へ移した ─ 画面が並べるものがブックマークだけではなくなった以上、
   パレットに «bookmark.list / ブックマーク» と出るのは嘘になっていた。旧名は
   `CommandFromName()` が別名として読み続けるので、既存の `keys.ini` の行はそのまま生きる。
3. **コマンドパレットはコマンドのまま** — ✅ `Ctrl+Shift+P` は据え置き。
4. **窓口を 1 つにする** — ✅ **モード方式**（下記の代替案）を採った。`Ctrl+P` の欄で
   `>` を打てばコマンド、消せば行き先。印は入力欄の中に文字として在るので、«今どちらか»
   を言うのも戻る道もそれ 1 つで足りる（`App::SyncPickerMode`、
   `CommandPalette::kPrefix`）。順位付けは持ち込んでいない。

**採ったのはモード方式（✅ 実装済み）。** 混合ではなく**モード**にする ─ 既定は行き先の
検索、入力欄で `>` を打つとコマンドに切り替わる（VS Code の `Ctrl+P` → `>`）。和音 1 つ・
窓 1 つで、薄まりも順位付けも起きない。満たしている条件は 2 つで、
**(1) 今どちらのモードかを入力欄が明示する**（印そのものが入力欄の中の文字）、
**(2) 順位付けを持ち込まない**。混合案は退けた ─ `d` の 1 文字に `file.delete` と
`Downloads` が並べば、行数の桁が違う分だけ頻繁な側が代金を払う。

現状（1 段目で入ったもの）:

- **ブックマークが先、開いているタブが後。** タブは追加であって置き換えではないので、
  ブックマークを探しに来た手が変わらない並びにしてある。
- **今いるタブは並べない**（`App::CollectOpenTabs`）。「ここへ行く」は「どこへ行く」の
  答えではないし、最初の選択がその行に乗ると `Enter` が何もしない画面になる。
  **他のペインのアクティブなタブは残す** ─ 分割中はそれも立派な行き先。
- **タブの行を選んだらそのタブへ移る**（フォーカスもそのペインへ）。同じフォルダを
  もう 1 枚開くのでは、開いてあるものを選んだ意味が無い。
- **タブの行では `Ctrl+Enter` を飲み込む** ─ すでに開いているタブに «新しいタブで開く» は
  無い（P3-1 の「無い意味を作らない」と同じ）。
- **種別を行に出す**（「ブックマーク」/「開いているタブ」/「ドライブ」）。同じフォルダが 2 行に出ること
  が普通にあり、しかも `Enter` の意味が行によって違うので、押す前に見えていなければ
  ならない。絞り込みにも当たるので「タブ」と打てば開いているものだけが並ぶ。
- **背面のセッションのタブは入れない。** あちらへ移るのは画面に出ていないペインごと
  入れ替わる別の操作（セッションの切り替え）で、行き先を 1 つ選ぶのとは重さが違う。
- **ドライブは末尾。** いつも同じ顔ぶれで並んでいる «背景» なので、探しに来る頻度が
  いちばん低い ─ 上に出すと、実際に開いているタブが画面の下へ押しやられる。
- **絞り込み欄はキャレットの動く入力欄**（`TextField`）。`←→`・`Home`/`End`・`Shift`
  での選択・`Ctrl+A`・クリップボードの 3 つが、Kite の他の入力欄とまったく同じに動く。
  数え方は 1 つしかない（`core/input/TextField.h`）。

## 6. フェーズ 4 — 性能とメモリ

### P4-1. メモリ削減（約 66 MB → 40 MB 台）— **M**

内訳の実測がまだ。まず何が食っているかを確定させる。想定される手当:
D3D11 デバイスの遅延生成と非アクティブ時の解放、`fs::Entry` の SoA 化
（現在は 1 件あたり `std::string` を持つ）、DirectWrite のフォントキャッシュ調整。
**先に計測すること。** 推測で削らない。

### P4-2. 巨大ディレクトリ対応 — **M**

10 万件クラスでの列挙・ソート・描画。列挙結果のストリーミング表示
（全件揃う前に描き始める）と、ソートの並列化。

### P4-3. 起動時間の実測と短縮 — **S**

現状の計測は `Start-Process` 経由でプロセス生成込みのため誤差が大きい。
アプリ内に計測点を仕込んで内訳（DLL ロード / D3D 初期化 / 設定読み込み / 初回列挙）を出す。

## 8. あえてやらないこと

判断を蒸し返さないための記録。

- **リボン UI / コマンドバー。** キーボード駆動を主軸に据えたので不要。
- **ファイル操作の自前実装。** コピー・移動・削除はシェル（`SHFileOperation`）に
  委ねる。進捗表示・競合解決・ごみ箱連携を自前で書き直すのは、ファイラーが
  データを失う最も一般的な原因。
- **シェルアイコンの同期取得。** `SHGetFileInfo` は 1 行ごとにクラウドプロバイダを
  呼ぶ。要件 3・13 と正面から衝突する。アイコン自体は取るようになったが、
  UI スレッドからは決して呼ばない ─ 見えている行の分だけをまとめて
  `kite_shellhost.exe` に投げ、時間制限付きで待つ（P2-10）。
- **プラグインシステム。** 当面。サードパーティコードを自プロセスに入れるのは、
  P1-1 / P2-10 で追い出した方針と正面から逆行する。
- **サードパーティライブラリの導入。** 起動時間・配布サイズ・ビルドの単純さを
  優先する。テストハーネスを自作しているのもこの方針の一貫。
